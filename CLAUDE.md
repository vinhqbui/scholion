# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Scholion: context-first version control for coding agents. Each task is an isolated jj workspace; decisions, attempts (dead ends) and notes are stored as records anchored to code; a deterministic, token-budgeted context pack hands any agent what it needs. The CLI is `scholion` with the alias `av` (same program); env vars keep the `AV_` prefix. Design: `docs/superpowers/specs/2026-10-18-agentvcs-design.md`. Implementation plans: `docs/superpowers/plans/` (Plans 1–5 are done; Plan 6, evaluation, is in progress; Plan 7, overlay index scopes, is merged; Plan 8, routing tasks to the agent that fits (backlog, agent profiles, `av next`), is merged; its evaluation is written but not run; Plan 9, closing the review loop (`next` offers reviews and merges first, rescues handoffs and abandoned tasks, waits; `av watch`), is merged. Plan 11, lean disk (finished tasks' workspaces reclaimed, the session footprint, `av disk`/`av gc`), is merged; Plan 12, lean builds (one cargo target dir per task workspace, line tables and no incremental cache, build output counted apart), replaced its shared build cache, which was unsafe, and lists what is left to do about build storage. Release 0.0.2 (tag `release/0.0.2`, `CHANGELOG.md`) is the first to ship `scholion-daemon` with bundled Postgres). The spec and older plans use the earlier name `agentvcs` and crates `av-*`. The plan files' checkboxes and some signatures lag the code; when they disagree, the code wins.

## Commands

Rust is pinned to 1.97.1 (`rust-toolchain.toml`); do not change it in an unrelated change.

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace                       # all green is the bar before any commit
cargo test -p scholion-daemon --test it api::submit_  # one crate's test binary, module / name filter
cargo test -p scholion-semantic --test it qdrant::NAME -- --exact --nocapture
cargo build --release -p scholion-cli           # -> target/release/scholion and av
scripts/smoke.sh                             # end-to-end against the Docker stack; --down also deletes volumes
docker compose -f deploy/docker-compose.yml up -d --build   # needs `export UID GID=$(id -g)` first
```

Test environment:
- Postgres tests use `scholion_testutil::TestDb`: a fresh database on `AV_TEST_DATABASE_URL` if set, otherwise an embedded user-space Postgres (downloaded on first run). No Docker needed.
- Qdrant tests silently skip (pass in ~0s) unless `AV_TEST_QDRANT_URL` (gRPC, e.g. `http://127.0.0.1:6334`) is set. A green workspace run does not prove Qdrant works.
- `warm_build_under_300ms` is `#[ignore]`d (timing).
- Docker Desktop without WSL integration needs Windows-drive paths for bind mounts; see the section of that name in `docs/reference.md` (the README is the short introduction; the reference holds the details).

## Architecture

Cargo workspace, `crates/*`, edition 2024. A daemon (axum, `:7420`) owns all state; the `scholion` CLI (alias `av`) is a thin HTTP client.

- `scholion-core` — shared types, `AvError`, and the traits every unit talks through (`traits.rs`: `Vcs`, `IntentStore`, `Semantic`). `lifecycle.rs` is the pure task state machine (`next(status, Event)`); illegal transitions are `AvError::IllegalState` → HTTP 422 (`Invalid` stays 400 = malformed input).
- `scholion-vcs` — **the only crate that touches jj-lib** (pinned `=0.46.0`). Repos are git imports; one jj workspace per task. After any jj-lib rewrite call `rebase_descendants()`. `ChangeId` is the jj *commit id* hex, so any snapshot/squash/rebase produces a new id. `remove_workspace` forgets a task's jj workspace and deletes its dir; `restore_workspace` re-creates it with the working copy *at* a commit (the task's head), not a child of it.
- `scholion-store` — Postgres `IntentStore` (sqlx, migrations in `crates/scholion-store/migrations/`, numbered `000N_*.sql`, embedded via `sqlx::migrate!`; two branches adding the same number break every DB test, so check `main`'s highest number before merging). A merged migration is never edited, not even a comment: databases store its checksum, and `tests/migrations_frozen.rs` pins each file's hash (add a line for a new migration). Postgres is the source of truth; the `repos` table (migration 0023) lists imported repos, written by the import and backfilled from the jj store at daemon start-up (`api::sync_repos`), and `GET /v1/repos` / `av repo list` read it. Writes that need embedding enqueue an `outbox` row in the same transaction (`outbox.rs`).
- `scholion-index` — tree-sitter (Rust, TS, Python) symbols, reference graph, skeletons and code chunks, stored in Postgres, incremental by content hash. A ref links by bare name to every same-named symbol (weight 1/k); `PgIndex::with_max_fanout` (`AV_INDEX_MAX_FANOUT`, off by default) drops names more than N others define, in `rebuild_edges` and in the overlay view queries (`view_pairs`), and `tests/overlay_equiv.rs` runs once under a cap of 1.
- `scholion-semantic` — `Embedder` (TEI, Ollama, `ScriptedEmbedder` fake) and `VectorIndex` (Qdrant, `MemoryIndex` fake). `Embedder::dimension` is `async` and fallible (the plan text says sync; the code is right). Qdrant is derived data, rebuildable with `av reindex`.
- `scholion-pack` — deterministic context packer, no LLM: seeds → candidates (structural, anchored records, semantic, live work) → scoring (lexical BM25 and semantic code hits count by rank, reciprocal rank fusion, `score::rrf_sim`) → budget split by section with spillover, and what the last section leaves upgrades earlier handles → progressive tiers (handle/summary/full) → session ledger so later packs reference instead of resend. Each pack stores a receipt (`rcp:<8 hex>`). Golden output in `tests/golden/`.
- `scholion-daemon` — `wiring.rs` builds `Config` from env and the `AppState`; `api.rs` routes (all under `/v1`); `worker.rs` drains the outbox into Qdrant every second; `embed_choice.rs` picks host Ollama `qwen3-embedding` first, else `AV_EMBED_URL`/`AV_EMBED_API_KEY`, else semantic off. If Qdrant/embedder fails, packs still return and are marked `degraded: semantic` (Postgres full-text instead). `ui.rs` + `ui.html`: the read-only dashboard at `/ui` (one static page, vanilla JS, embedded with `include_str!`; it only reads `/v1`; the Teams column reads `/v1/office`).
  - **`flow.rs` holds the Plan 3 lifecycle operations (submit, and next handoff/claim/review/merge/undo/backup).** The plan says a separate `av-flow` crate; that was overruled because each op needs `snapshot_and_index` from `api.rs`. Their tests go in `crates/scholion-daemon/tests/api.rs`; concurrency tests (many agents at once) in `tests/swarm.rs`. Both share `tests/common/mod.rs` (`env()`, `env_with()`, `env_with_vcs()`, `start_task`, `submit`, `edit_greeter`, `call`). Every crate's `tests/*.rs` are modules of one test binary, `it` (`tests/main.rs`, `autotests = false` in its `Cargo.toml`; add a `mod` line for a new file): one executable per crate instead of one per file, since build output is the disk agents spend (Plan 12). Workspace operations on one task take `AppState::lock_task` first, then `flow::fence` (refuses writes under an older claim generation, header `X-Av-Generation`).
  - `ext.rs` — extension points for code built on the daemon (the commercial edition): `router_with` (extra routes behind the token), `AppState::with_extension`/`extension` (typed services), `subscribe_events` (lifecycle events in process), `MergeGuard` (asked before submit (`Guarded::Submit` with the changed paths), approve and merge; `AllowAll` here), `AppState::with_mcp_tools` (extra `/mcp` tools; the size guard in `tests/mcp.rs` counts Community tools only), `UsageSink` (`POST /v1/agents/{name}/usage`; `NoUsage` stores nothing), `AppState::put_profile` (upsert `agent_profiles`), `AppState::migrate_extension` (an extension's own migrations in its own Postgres schema with its own `_sqlx_migrations`, so its numbers never meet ours; tests in `scholion-store/tests/extension.rs`). A binary built on them starts through `run_with(cfg, customize)` (`serve.rs`): `scholion-daemon`'s whole start-up (lite-mode Postgres, state, repos sync, worker, backups, graceful shutdown) with a step that gets the built `AppState` and returns it plus extra routes; `serve_with` takes the listener and a shutdown future (tests in `tests/serve.rs`). Keep them stable: agentvcs builds on them.
  - `routing_api.rs` — Plan 8: `/v1/agents`, `/v1/backlog` and `POST /v1/backlog/next`. `next` (Plan 9, `choose` then `act`) offers, in order: reviews of others' in-review tasks (never the owner; only agents that fit the item's tags, unless only the owner fits; reserved 600 s per reviewer in `AppState.reviews`; approved ones say "merge it"), then the agent's own conflicted tasks (approved, merge conflicted: `from: conflicted` with a `next` that says sync, resolve, re-check, resubmit; resumed via `flow::resume_as`; another agent may claim one, still conflicted, once the owner's lease ran out), then handoffs (claimed; untagged ones keep their item's tags with the same exception), abandoned open tasks (lease ran out; the owner resumes via `flow::resume_as`) and queued items, ranked by the pure rules in `scholion-core/src/routing.rs` (`order_for_excluding`: the agent that handed a task off neither takes nor holds it). A profile's `max_open` (migration 0024; NULL = no limit) caps a team's open tasks: `within_limit` then keeps only reviews and the agent's own abandoned tasks, and the empty answer carries `at_capacity`. A backlog item with `after` (migration 0026: `after_ids`, resolved from an item id or title slug when posted) is left out of `choose` until every item it lists has a merged task; `BacklogEntry.waiting_on` (computed in SQL) names the rest and `av backlog` prints it. Targets (Plan 10 A3, migration 0027; `/v1/targets`, `PUT /v1/backlog/{id}/target`, `av target`): an item counts toward at most one active target of its repo (`backlog.target_id`), progress (items/queued/working/merged) is computed in SQL (`TARGET_SELECT` in `pg.rs`), a target is named by id or title slug; targets never affect routing. `wait_secs` re-runs `choose` when woken (cap `MAX_WAIT_SECS` 50, `AppState::with_max_wait`): by an event of `WAKING_KINDS` from the one in-process event feed (`submit`, `approve`, `merged`, `handoff`, `abandon`, …; not `checkpoint`), by `AppState::work_changed` (backlog post/drop, profile put/delete, which are not events), else every `WAIT_TICK` 10 s for what only time releases (leases, review reservations; `with_wait_tick`, the wake tests set 60 s); `dry_run` returns `{would}` and takes nothing (`av watch` polls it). `take` (`review`, `merge`, `work`; empty = all, `av next --take`) keeps only those kinds of choice, so a review-only agent is never given backlog work and a worker is never offered (or reserved) others' reviews. MCP tools resolve `task_id` as id, slug or `repo/slug` (`mcp::task_ref`). Tests in `tests/routing.rs` and `tests/swarm.rs` (`swarm_loop_runs_backlog_to_merged`). An agent's MCP name is resolved through profile aliases at `initialize`. `start_task` with no `title`/`goal` is `next`; the tool list is size-guarded in `tests/mcp.rs`.
  - `disk.rs` — Plan 11: a merged or abandoned task's workspace and scratch dir (`<repo>/.scratch/<slug>`) are removed once it has had that status for `AV_WS_RETAIN_SECS` (default 3600, `never`, `0` = inside the merge/abandon itself, which then answer `workspace: removed`); whatever the retention but `never`, the merge/abandon removes the workspace's `target/` at once (`reclaim_task` answers `(workspace, build)`, `build: removed|none|kept`, event `build:reclaimed`); "since" is the newest status event (`IntentStore::tasks_with_status_since`, no migration). The sweep (`spawn_sweep`, every `RECLAIM_TICK` 60 s, started in `serve.rs`), `POST /v1/gc` (`dry_run`, `retain_secs`, `build_cache`; each reclaimed workspace says `build_bytes`) and `GET /v1/disk` (per repo: workspaces with status/size/`build_bytes` (its `target/`, Plan 12)/age/`reclaimable`, scratch, the `.cache` dir, store; `outside`; totals incl. `build_bytes`). Each removal takes `lock_task` and re-reads the status; `flow::undo`/`revert` restore the workspace (`ensure_workspace`, without `set_workspace`, which would reset the head). Deletes only through `under_ws_root`. `POST /v1/footprint` keeps the hooks' reports in memory (`AppState.footprints`, one per session, newest first, 200), shown as `outside`; the daemon never deletes those paths. Tests in `tests/disk.rs`.
  - `build_cache.rs` — Plan 12: for a repo whose trunk has a root `Cargo.toml`, writes `<ws_root>/<repo>/.cargo/config.toml` (`incremental = false`, `debug = "line-tables-only"`, `package."*".debug = false` for dependencies, **no** `target-dir`: each workspace builds into its own `target/`, which the reclaim removes with it; measured 4.3 GB vs 21 GB per full `cargo test` build of this repo) at import and in `sync_repos`; rewrites only a file whose first line starts with `# written by av:` (so Plan 11's shared-target file, which let `cargo test` in one workspace run another task's binary, is replaced). `AV_BUILD_CACHE=off` writes none. `scholion-vcs` never snapshots a workspace's top-level `target/` (`AGENT_IGNORES`). Test in `tests/disk.rs`: `two_workspaces_of_one_repo_never_share_a_target_dir` runs `cargo metadata` in each. `deps_cache.rs` (Task 5): reclaiming a task's build output first keeps its registry/git dependency units in `<ws_root>/<repo>/.cache/deps-target/` and a new or restored workspace's `target/` starts with them: `*.rlib`/`*.rmeta`/`*.so` hard-linked (rustc replaces them), `.d`, `.fingerprint/` and `build/` copied (rewritten in place); a unit is shared only when its dep-info lists sources under cargo's `registry/src/` or `git/checkouts/`, so the repo's own crates never are; both run in the background (`disk::retire_build` renames `target/` into `.cache/reclaim/` and harvests from there; `disk::seed_dependencies` builds in `.cache/seed/` and renames into the workspace under `lock_task` only if it still has no `target/`; `sync_repos` clears both at start-up; events `build:reclaimed`, `build:seeded`); every file in the cache keeps its time rounded down to the second (Docker Desktop's Windows-drive mount drops the fraction of a time that is set, so copies would predate links and cargo would rebuild); `GET /v1/disk` counts a multiply linked file once. What remains (workspace slots with warm targets) is in `docs/superpowers/plans/2026-11-03-scholion-plan-12-lean-builds.md`.
  - `history.rs` — cold start (Plan 13 Phase 2): `mine` walks `Vcs::history` (every ancestor of trunk, newest first; `JjVcs` reads its own store, no `git`) and writes one `note` by `MINED_AUTHOR` (`git`) per commit `scholion_core::history::worth_mining` keeps (one parent, not housekeeping, ≥ 20 chars of message without trailers) that touched 1–25 files, anchored to them, `change_id` = the commit; all on one task per repo (`git-history`, owner `git`, set merged at once, no workspace; `history_task` finds it); commits already mined are skipped. Called by the import (`AddRepo.mine_history`, the job's `mined_records`; a failure is logged, not fatal) and `POST /v1/repos/{name}/history` (`av repo mine`). `scholion-pack` ranks mined records by `score::MINED_FACTOR` (0.5) and puts them last in `records_at`; `record_texts` labels them `note (git <sha7>)`; `derived::why` returns the blamed commit's mined record when no task owns it. Tests in `tests/history.rs`.
  - `office.rs` — Plan 10 A3, read-only, for the dashboard: `GET /v1/office` (per agent: profile, open / in-review tasks, reviews reserved in `AppState.reviews`, last timeline entry, state `working`/`quiet`/`reviewing`/`idle`; quiet = open tasks none written to within a lease, reckoned as `abandoned_tasks` does) and `GET /v1/agents/{name}/timeline` (`PgStore::agent_timeline`: records by author, `started`/`claim` events by `payload.agent`, `review_verdicts`, submits attributed to the owner when no later claim, merges by `merged_by`). No new tables. Tests in `tests/office.rs`.
  - `mcp.rs` — the MCP server at `/mcp` (JSON-RPC over streamable HTTP, plain JSON responses; hand-rolled, no SDK). Each tool is an in-process request to `api::routes()`, so tools behave exactly like the HTTP API. A session remembers every task it started or claimed (Claude Code subagents share their parent's session, checked with a logging proxy); without `task_id` a call uses the only one, else the only open one, else refuses and names them (`target`). Tests in `tests/mcp.rs`.
- `scholion-agentrun` — what running an agent CLI needs and the benchmark does not. `AgentCommand` is the builder (program, args, cwd, ordered `env`/`env_remove`/`env_clear` (a runner starts the agent from an empty environment), `path_prepend`, `max_budget_usd` appended last as `--max-budget-usd`, deadline, `stop_flag` (another thread, such as a budget watchdog, kills the run early: `RunResult::stopped`), `events_path` for stdout, `stderr_path`); `run()` returns a `RunResult` (exit, `killed`, wall time, events path, usage totals, the parsed `ParsedSession`). Underneath, `process` (`run_with_timeout` kills the child's whole process group at the deadline, `run_until` also when a flag is raised; `shell` logs stdout and stderr to a file) and `events` (parses `claude -p --output-format stream-json`). It does not know which CLI it runs, nor tasks, daemons or arms: argv, variables and prompts are the caller's. `slots`: host-wide slots (`take`, `wait_for`; OS file locks on `<dir>/slot-<i>.lock`, freed when a process dies) for agents (`$AV_HOME/agents`, `AV_MAX_AGENTS`) and builds (`$AV_HOME/builds`, `AV_MAX_BUILDS`), and the `$AV_HOME` default the CLI uses, so every process that starts agents or runs checks on a host shares one budget. Used by `scholion-bench` (`run_session` builds its claude command with it; `events` is re-exported as `scholion_bench::events`) and meant for the commercial runner (Plan 10 B5).
- `scholion-bench` — the Plan 4 benchmark harness (`scholion-bench check|run|report|calibrate`). Pure analyzer (`events`, `metrics`, `report`, `stats`, `calibrate`); only `runner`/`orchestrate` start processes and only `run --confirm` spends money. Tests use a fake `claude` script and, for the av arms, a real daemon. Tasks and the run guide: `bench/` (`bench/README.md`). `run` removes a valid session's copy after verify (the av arms' import copy, and the task is abandoned) unless `--keep-work` (`RunConfig::keep_work`). `bench/tasks-relay` is E4, the knowledge relay (arms `cold` (no lessons, the control), `baseline`, `notes`, `av`; `--jit-hooks`; `--price-per-mtok` for models Claude Code cannot price, e.g. DeepSeek; `--noise N` (`noise.rs`, E4 at scale) adds N seeded irrelevant notes from the base tree's files to both `NOTES.md` and the av records, `scholion-bench noise` prints them; design in `bench/results/2026-11-e4-scale/DESIGN.md`). The av arms run on hooks + CLI unless `--av-mcp`; a spec's `path_prepend` puts dirs (the venv with pytest) first on the agent's PATH. Plan 6 adds `retrieval` (offline E1: scores first packs against three baselines, `--no-pack` needs no daemon, `--reuse-run ID` re-measures a new packer on repos an earlier run imported) and `mine` (builds retrieval tasks from a repo's history); task set and how to run it in `bench/retrieval/README.md`.
- `scholion-cli` — clap subcommands mirroring the API. `local.rs`: `av up`/`av down` (lite mode: the daemon runs its own Postgres when `AV_DATABASE_URL` is unset, `embedded_pg.rs`) and `av init`; `agents.rs`: `av init --for codex|grok|gemini|cursor` merges the MCP server into those CLIs' config files (Grok, Gemini and Cursor also get an `X-Av-Agent` header; Cursor's is `~/.cursor/mcp.json`). `av init --for mcp-json --path FILE` merges `{type: http, url, headers: {X-Av-Agent}}` into any `mcpServers` JSON file; `X-Av-Agent` is the global `--agent` name. Muse Code's own settings path is still unverified (`integrations/muse/README.md`); point `--path` at it once you know the file. Plan 8 adds `av agent set|list`, `av post`, `av backlog [drop]`, `av next` and `av handoff --needs`; Plan 9 `av next --wait` and `av watch` (`watch.rs`: polls a dry-run `next` and runs an agent command when work fits; the CLI may start processes, the daemon never does; `--max-agents N`/`AV_MAX_AGENTS` caps agents per host with N locked slot files in `$AV_HOME/agents`; `av validate --max-builds N`/`AV_MAX_BUILDS` runs the command and checks only while holding one of N in `$AV_HOME/builds`; both through `scholion_agentrun::slots`). Plan 11: `disk.rs` renders `av disk` and `av gc` (`--json` prints the answer); `crates_scope.rs` (Plan 12 Task 2): `av validate` replaces `{crates}` in a check command with `-p …` for the members a change touches plus their path dependants of every kind (`cargo metadata --no-deps`, run by the CLI), else `--workspace`; the daemon's `GET /v1/tasks/{id}/checks` gives it `changed`. `target_dir.rs` (Plan 12 Task 3): in a cargo workspace, `av validate` (command and checks), `av-wrap.sh` and (only when the user's env names a target dir, as shell code in `$CLAUDE_ENV_FILE` that finds the nearest `.av-task` per Bash command) the session-start hook set `CARGO_TARGET_DIR=<workspace>/target` and unset `CARGO_BUILD_TARGET_DIR`, since a user's shared target dir would make `cargo test` run another task's binary. `footprint.rs` is the pure scan/diff of heavy dirs (`HEAVY` names, depth 4, ≥ 1 MiB growth) the hooks use; `av up` rotates a `daemon.log` over 50 MB. Finds its task via the nearest `.av-task` file in the workspace; `AV_URL` / `AV_SESSION` override.
- `scholion-testutil` — `TestDb` only.

`integrations/` holds the agent glue: `claude-code/install.sh` installs `SessionStart` (prints a pack), `PreToolUse` on `Read|Edit|MultiEdit` (other tasks' records about that file, `GET /tasks/{id}/records/at`, each record once per session), `PostToolUse` (checkpoints) and `Stop` (asks once per session to record changes no record explains, `GET /tasks/{id}/unrecorded`; then, if a dry-run `next` finds work for the agent, blocks the stop and says to call `start_task`, waiting up to `AV_HOOK_WAIT_SECS` (default 600, 0 = off) and at most `AV_HOOK_MAX_CONTINUES` (default 20) times per session; `install.sh` sets its timeout to the wait + 60 s) hooks that call `scholion hook session-start|pre-read|post-edit|stop`; `generic/av-wrap.sh` wraps any other agent. Plan 11: in a task, `session-start` creates `<repo>/.scratch/<slug>` and appends `export AV_SCRATCH=…` to `$CLAUDE_ENV_FILE`; task or not, it saves a footprint snapshot (`$AV_HOME/footprint/<session>.json`) and `stop` diffs against it, blocks once at `AV_FOOTPRINT_WARN_MB` (default 512) and posts the additions to `/v1/footprint` (`AV_FOOTPRINT=off`, `AV_FOOTPRINT_ROOTS`, `AV_FOOTPRINT_SECS`). The CLI tests turn the footprint off by default. Pack code items carry path, lines and signature, not bodies, because Claude Code re-reads a file before editing it (see `bench/README.md`, "Haiku runs").

Invariants worth not breaking: record summaries ≤ 200 chars and records are append-only (newer ones *supersede*); `submit`/`handoff` are refused without an intent plus at least one decision/attempt/note/handoff record; `main` advances only via `merge` (or `revert`, which adds a commit); the daemon never runs repository commands (validations/checks are attestations reported by clients); workspace paths returned to clients are host paths (`ws_host_root`), not container paths; auth is the optional shared `AV_TOKEN` (every route but `/healthz` and `/ui`), so compose still binds everything to `127.0.0.1`.

## Working conventions

- `main` is the base. Start each change on a branch off `main` and land it through a pull request; prefer one PR per change over stacked PRs (a PR stacked on another merges into that branch, not `main`).
- Work is TDD: failing test first, then implementation, then fmt + clippy + tests. See `CONTRIBUTING.md`.
- Agent-facing text (pack output, MCP tool descriptions, hook messages) says `av`, not `scholion`: it is shorter for agents to type and both names are always installed.
